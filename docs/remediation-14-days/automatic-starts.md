# Automatic task starts

The user authorized automatic starts and resumes, updated to **every five hours**, with **one or two eligible tasks per period**. One interval replaces the thirteen daily schedules, which are disabled. The first check is **2026-11-02 at 19:26 Asia/Ho_Chi_Minh (12:26 UTC)**; subsequent checks are five hours apart through November 15. They use the existing BidTool project and reserved implementation threads. The next run checks every due unstarted package, including packages blocked on previous days.

## Eligibility and concurrency

A package becomes eligible when its start date has arrived, its prerequisite implementation PRs have merged, and its writable files have no active owner. Issue closure or a green check alone does not establish that prerequisite code is on the target branch. Automatic starts do not create an unreviewed stack. If a prerequisite is still open or draft, record that blocker and check again at the next five-hour check.

Dispatch at most two tasks total (initial starts plus resumes) per five-hour period. Start one or two when eligible; zero is correct when blocked. Keep at most two remediation implementation threads active at a time. Count preparing, starting, queued, running and waiting threads as occupying a slot. Read existing threads and PRs before sending a start message. Use the stable per-package request key below so duplicate coordinator delivery cannot launch a second turn. A package already started or with an implementation PR is not a new task. Apply the Sol continuation rules below instead of duplicating its initial start. Never interrupt an active turn or answer a pending approval automatically. Honor later user pauses, cancellations and scope changes before dispatching anything.

Respect the file handoffs in the [delivery schedule](./README.md). In particular, R2 waits for the R1 storage handoff before editing shared storage code. R5 and R11 must agree their shared search/workspace lock contract before either changes the other's files. R14 follows R5, and R6 follows R14. Never start two owners of overlapping files.

## Sol implementation loop

The user also authorized GPT-6.1 Sol workers to keep iterating until each scoped PR is ready. All fourteen reserved threads are configured for `gpt-6.1-sol` on `codexCLIProxy`, with `reasoningEffort: high`. Retain these threads and worktrees; this is not a request for extra workers.

Each worker repeats implementation, affected checks, complete-diff review and focused fixes within its run until the package's local acceptance passes and its scoped PR is prepared. Record the actual results and remaining evidence. Missing Docker, database or native-platform proof keeps the PR draft; do not manufacture evidence or mark drafts ready automatically. PR readiness here means code and available validation are prepared for review, not that reviewers have approved it.

The five-hour coordinator may resume unfinished work whose previous turn has ended, including recoverable failed or interrupted turns, only when the thread has no active run or pending human request, dependencies still pass, its scope is free, and the next action is concrete. Read the latest outcome and actual worktree/PR state first. A ready PR, closed PR, merged package or unchanged environment/dependency blocker gets no new turn. An interrupted tool action with an unknown outcome must be resolved before retrying. Never reset or discard existing work.

For each continuation use `bidtool-20261102-sol-continue-<package>-<last-ended-run-id>` as `clientRequestId`. Record that key before dispatch; at most one continuation per package per five-hour period. Duplicate triggers observing the same ended run reuse the key. Count continuations against the same two-thread limit and prioritize actionable unfinished packages before new starts. Do not poll or watch workers/PRs, or create a timer loop. Workers iterate within a run; the five-hour interval provides bounded resumption through November 15. After that date, report unfinished work without new starts or continuations.

The registry identifies the exact existing threads and GitHub tasks. 1. Confirm actual time in Asia/Ho_Chi_Minh. Day 1 work may resume on November 2; original package start dates remain lower bounds. Read intervalAnchorUtc and intervalMs in the local automation record and compute the current five-hour period. Atomically claim it by creating periods/<period-index>.claimed under the run directory; an existing claim means dispatch nothing. Keep the claim after partial failure, and record intent, request keys and results there. Late/coalesced deliveries do not create extra batches. After November 15, disable the recorded interval with schedule_task(enabled:false) and report backlog without starting or resuming work. Disable it early when all work is prepared or complete.
2. Inspect all fourteen thread states with `t3_thread_read` and the actual GitHub PR state using `gh-axi`. Resolve dependencies from task-linked implementation PRs and their merge commits, not from stale registry status. A missing or corrupt registry is a blocker, never a reason to invent threads or paths.
3. List due candidates in the delivery-table order. Skip closed/merged packages, ready PRs, active threads, unmet prerequisites and active file conflicts. Consider unfinished work only under the Sol continuation rules above. Apply the R8 stage rules above. Do not launch beyond either the two-thread limit or the two-dispatch period limit.
4. Start only the original reserved top-level thread with `t3_thread_send`. For an initial start use `clientRequestId: bidtool-20261102-auto-start-<package>`. For R8's final stage use `bidtool-20261102-auto-r8-final`. For unfinished work use the Sol continuation key above. Keep each message stable across retry deliveries. Do not create a replacement thread or delegate a new worker.
5. The start or continuation message identifies the issue, package brief, exact writable scope and stage, and requires the Sol implementation loop above. Before dispatch verify the configured provider/model on the inactive thread with `t3_thread_configure`; set `instanceId: codexCLIProxy`, `model: gpt-6.1-sol` and `reasoningEffort: high` if needed. Stop on an unavailable model instead of silently substituting. Instruct the worker to verify its T3-managed worktree, inspect/fetch current `origin/main`, and bring required merged changes into that branch with a non-destructive fast-forward or merge. Preserve local edits and published history. The worker implements, runs focused checks, commits/pushes and opens a scoped PR using `/file-pr`; `link_pull_request` is its next tool call after PR creation. Missing acceptance proof requires a draft PR. The R8 foundation PR references the task without closing it.
6. Record each returned run ID, thread link, request key and observed PR in the local registry. Summarize starts, active work and blockers in the coordinator's own thread using exact returned thread links. A later five-hour check rechecks blocked, unstarted work. Do not poll workers, monitor PRs, or start servers from the coordinator.

The coordinator may update local orchestration records. Implementation stays in the assigned worktrees. Merging PRs, marking drafts ready, release publication, deployment, production-data access and destructive cleanup remain outside this automation's authorization. Scheduled runs require the T3 host to be available; delayed delivery does not extend the authorized window.
